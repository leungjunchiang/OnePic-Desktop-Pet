# v0.23.306 北京时间审计

## 已确认的根因

`DisciplineWorkspace._render_summaries()` 与 `_show_history_day()` 原来用
`occurred_at[11:16]` 直接取 ISO 文本的钟点。因此收到
`2026-10-01T03:36:00Z` 或 `+00:00` 时会展示 **03:36**，没有转换为北京时间 **11:36**。
今日事件、历史事件、待说明选项和恢复的搭子事项均存在这种路径。

这轮通过真实 Qt 组件注入上述服务端格式，验证今日与历史均显示 11:36。
没有读取用户截图所对应的私人数据库记录，因此该记录的精确原值不能凭截图确定。
确认的是实际代码路径、真实数据库字段类型与 UTC 返回形态，以及相同输入的回归复现。

## 17 项核查结果

| 项目 | 结果与实现 |
| --- | --- |
| 1. 03:36 为什么出现 | 今日、历史与待说明 UI 直接截取 UTC ISO 文本，不经过转换。 |
| 2. 原始数据库值的时区 | `lili_discipline_events.occurred_at` 为 `timestamptz`，保存绝对时刻；UTC 会话的 JSON 带 `+00:00`。实际用户行未读取；已用相同 UTC 示例复现。 |
| 3. 漏转换的函数 | `discipline_ui.py` 的 `_render_summaries`、`_show_history_day` 改用共享 `format_clock`；包括五处正文/选项时间。 |
| 4. 同类问题 | 恢复的训导消息、经济/食品事件、闹钟列表和编辑器、提醒 Toast、待办云端 fallback 与倒计时日期。纪律与聊天历史还存在混合偏移 ISO 文本排序问题，改为真实 timestamp 排序。 |
| 5. 之前的 datetime.now() | window 的日历/行为/提醒、discipline 的本地日边界、聊天/日记/记录/闹钟/计划相关本地 manager 默认时钟、Qt 当前日期，曾依赖系统时区。现在业务时钟转 Beijing；三个仅取 epoch 的调用保留，分别用于 FocusQualityTracker 和 Todo 重试期限，不产生日期或显示时间。 |
| 6. datetime.utcnow() | 当前 `src` 未发现这种调用，没有新增 naive UTC。 |
| 7. naive datetime | 存在旧本地 JSON 与输入墙钟。共享工具明确旧本地 naive = 北京墙钟；服务端兼容 naive = UTC，分别使用 `parse_timestamp` / `parse_server_datetime`。新记录带偏移。 |
| 8. FocusSession 数据库 | 原始事实 `lili_focus_segments.start_at/end_at` 是 `timestamptz`。上传/数据库保存同一绝对时刻；客户端北京自然日裁剪、区间并集和时长算法保留。 |
| 9. heartbeat 数据库 | `lili_focus_presence.last_seen/session_started_at` 与 `lili_focus_device_presence.last_seen` 为 `timestamptz`。TTL 按 aware 时间差判断；恢复状态不制造开工。 |
| 10. 纪律/互动/训导数据库 | discipline 的 occurred_at、visit_events 的 created_at/responded_at、coaching_cases 的 created_at/updated_at/accepted_at/closed_at 均为 `timestamptz`；真实库发布门禁检查类型，不读取个人内容。 |
| 11. actual_work_start | 客户端报告与账本共用 `get_actual_work_start`；固定北京当天 06:00 后首次真实 session start，恢复/合成 presence 被排除。服务端既有 `lili_actual_work_start_clock` 同样固定北京，旧设备 utc_offset_minutes 不再决定业务时区。跨06:00的旧会话不制造新开工。 |
| 12. 今日/昨日/本周 | 业务 now、报告锚点、计划、账本、免战、周一、自然日边界均从北京日期取得；UTC Sep30 18:30 归 Oct1 02:30，UTC Sunday16:30 归北京Monday。 |
| 13. 免战牌 | 创建时间与生效日期来自北京时钟；UTC Sep30 19:36 对应 Oct1 03:36 的今日免战。今日、历史显示均共享转换。 |
| 14. 工作报告 | 原时间轴已经按北京区间计算，本轮修正传入其他时区 now 的锚点和实际开工口径；日/周/月/年继续从同一原始事实派生，未上传报告副本。 |
| 15. 统一 helper | 复用现有 `time_service.py`，新增 now_beijing/to_beijing/parse_server_datetime/beijing_day_start，统一 format_clock/parse_date/parse_datetime。旧 now_local API 保留但语义固定北京；各处时区常量复用同一对象。 |
| 16. 直接 +8 小时 | 没有。Python 用既有等价 `timezone(+08:00, "Asia/Shanghai")`，不要求 Windows 额外安装 tzdata；SQL 用 `AT TIME ZONE 'Asia/Shanghai'`；Qt 编辑器用 UTC+8 QTimeZone。时长、TTL、补时均不加偏移。 |
| 17. 测试 | 新增 `test_beijing_timezone.py` 21 项，覆盖五种显式偏移、午夜、计划迟到16分、免战、周边界、06:00、真实今日/历史 UI、Qt 闹钟、工作报告与账本一致、旧数据语义。独立子进程设 TZ=UTC/Tokyo/Los_Angeles；只改测试子进程环境，不改用户系统时区。 |

## 页面与数据流

- 首页/搭子详情：沿用小心跳和统一 TTL；最后确认的相对时间使用 aware 差值，互动绝对钟点经服务端解析器。
- 专注今日/计划/训导/今日小牌子/头顶卡：北京日期选择今日/昨日，计划 09:00 与18:00 保持用户配置墙钟；补时仍使用区间并集。
- 记录今日/本周/历史：UTC事件先转换再显示，混合偏移按瞬间排序。配置墙钟与已结算业务日期不被误当 timestamp 转换。
- 工作报告日/周/月/年：北京自然日/周边界；只把 actual_work_start 与迟到使用06:00规则，累计专注仍按00:00自然日，不把全系统日统计改成06:00工作日。
- 投喂/互动/经济记录/桌面Toast：已读绝对时间本地转换；关闭通知与订阅继续独立。
- 闹钟/待办/倒计时：墙钟输入附北京时区，服务端绝对 due_at fallback 转北京；Qt 不再截掉时间偏移。

## 数据库与兼容

没有新增表、列或数据回填。`supabase/beijing_time_contract.sql` 在现有原子部署 bundle 的最后替换既有内部函数；保持不授予 authenticated 直接执行权限。它忽略旧设备偏移，按北京界限查询原始 session start，并保留真实开工/恢复来源过滤。

`scripts/verify_beijing_timezone.sql` 在真实数据库事务内检查实际类型、UTC JSON形态、北京日/周、09:00墙钟、跨06:00会话和旧US设备metadata；夹具使用合成账号，最后 rollback。发布流程沿用既有数据库门禁，校验失败不发布安装包。

旧数据带 `Z` / `+00:00` / `+08:00` / 其他偏移的，转换保留同一时刻，不修改原始事实。无偏移历史记录的来源无法仅凭字符串恢复，按明确来源契约解释，不猜电脑曾使用哪个时区。若旧版本已经把错误业务日写入纪律结果，不能批量按 occurred_at 重写：日报可能在次日00:00结算昨天，免战可能明确指定某一天。保留这些语义日期；原始事实推导的实际开工、今日聚合及新创建事件使用北京口径。缓存搭子互动没有另行指定业务日，读取时可按瞬间恢复北京日期。

固定+08等价实现适用当前应用的现代业务日期；不尝试重现1992年前中国历史夏令时。

资料核对：[PostgreSQL 日期时间类型](https://www.postgresql.org/docs/current/datatype-datetime.html)、[Supabase 数据库配置](https://supabase.com/docs/guides/database/postgres/configuration)、[Supabase 更新日志](https://supabase.com/changelog)。`timestamptz` 保存绝对时刻，返回偏移由会话决定；显示转换由应用完成，计划墙钟与持续时长分别处理。
