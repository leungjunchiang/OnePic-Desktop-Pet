# v0.23.329 闹钟点击崩溃排查

## 真实证据

Windows 本机 2026-10-10 11:30:00 自定义 MP3 的 MCI 返回 open failed: 277；随后 QtThreadAudio 连续播放至约 35 秒。11:30:36 用户点击 dismiss，按钮已返回，最后一条音频记录为 media.alarm.worker.stop；native-crash 为无 Python frame 的 Fatal Python error: Aborted。没有后续 alarm.action.enter、线程完成或音频清理完成记录。可以定位在音频停止/原生清理边界，日志不足以给出 FFmpeg 内部 C++ 栈，不将网络错误当作这次 Abort 的根因。

## 修复边界

Windows create_qt_alarm_audio 返回 QtProcessAudio，继承原接口与信号，让现有 AlarmCard、试听、AlarmAudioService 继续管理所有权、重复操作和清理。真正 QtThreadAudio 只在无窗口辅助进程内运行，复用既有解码、循环和有限断点恢复。主进程收到退出确认才释放关闭的卡片。停止超过 2 秒时只 kill 这个解码进程；按钮路径不执行 waitForFinished/wait/join。运行中解码进程异常退出仍走系统声音回退；明确关闭不误报错误、不恢复播放。退出门禁按 closed 判断线程/进程两类后端。

辅助进程只通过当前用户可访问的随机 QLocalServer 名称通信，不访问远端、不读取账号、不进入正常单实例/窗口/托盘初始化。主进程退出后控制通道断开，子进程立即结束，避免音频孤儿进程。源码启动明确传入包目录；冻结版本重用 Lili.exe 的早期辅助参数。没有修改全局环境或安装系统软件。

## 验证

新增 tests/test_alarm_audio_process.py 验证真实独立播放、GUI 忙碌仍计时、立即取消、os.abort 故障注入、停止不返回的故障注入、异常退出只通知一次、冻结入口，以及 start/snooze/dismiss 三个按钮的单次处理和清理时序。脚本 scripts/verify_packaged_alarm_audio.py 纳入 Windows release build，在实际冻结 exe 上验证 IPC 与停止；有音频设备时额外验证静音播放，无设备明确仅验证握手。

用户现有 MP3 只读、音量零播放 36 秒，停止前播放进度超过 30 秒，期间 GUI 定时器触发超过 1100 次；停止后辅助进程闭合一次，无错误。此重放与 Abort 注入证明主进程隔离，不能声称拿到了原生解码器内部精确栈。

所有回归使用临时闹钟和静音测试音频，真实音频不进入源码、测试夹具或发布包。无数据库结构、远端请求、计时事实和闹钟配置变更。无需重置卡。
