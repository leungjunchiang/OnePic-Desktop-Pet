# v0.23.349 · 播放模式与未接收队列

用户反馈已手动设为顺序播放仍被拒绝，并希望原有随机、列表循环、单曲循环也能起播。

## 已确认的证据与边界

本机 2026-10-26 日志显示模式设置 helper 在原生命令读回后进入 UIA 动作阶段并失败；另一请求选择《空中怪车事件》，二十五秒内系统仍返回《我在何地》且已暂停。后者是目标曲没有获得播放确认，不能解释为账号掉线或会员失效。

同一天在用户保留的歌词详情页调用产品接口，随机、列表循环、单曲循环、顺序四种模式都能设置并读回；同一《空中怪车事件》约 3.75 秒确认起播。说明原故障间歇出现，当前不能完整复现其触发时序，也不能要求用户必须手动收起歌词页。

## 行为修改

1. 顺序模式仍是 Windows 三十首临时队列的内部执行方式，防止单曲重复或客户端随机提前重选。用户不必预先调整 QQ 模式；六毛自动切换，暂停后还原。Mac 保留既有单曲隔离方案，未将 Windows 原生命令移植到 Mac。
2. QQ 在应用新模式后可能重建旧控件，动作返回假／抛错不能直接否定已生效状态。现在不论动作返回值如何，均重新读回目标模式才判成功；真正未改、控件读取失败和取消仍不放行。还原同样以实际读回为准。
3. 用户在听歌中手动改为另一个模式，下次主动选曲以最新读到的模式为还原目标。失败清理不再强制将与目标不同的现有模式覆盖成旧模式。
4. Windows 原生队列新增至多一次的投递恢复，必须同时满足：投递前是明确的旧暂停／停止曲；至少两次观察且两秒内同歌、歌手、专辑、状态、原始位置及时长都不变；独立读取的唯一 QQ 主窗口标题仍明确等于该旧曲与歌手。通用 QQ 标题、多个主窗或异常均不支持重试，防止 GSMTC 过时而目标已播放时重启歌曲。
5. 补发的是同一位置至轮末的同一 ID 队列，仍经过模式、进程和元数据校验；最多两次投递且沿用初次二十五秒期限，不无限重试、不换歌、不自动点击播放／付费。出现目标、Changing、媒体缺失或任何新状态／时间轴／曲目即永久禁止本次补发；取消先于补发。
6. 未确认且仍为旧暂停曲时，提示实际停留的歌名及状态，明确本次曲目未开始。原歌单保留，续播不启用；不再只说无法确认的泛化状态。

## 验证

新增回归先在旧代码重现模式动作已生效仍误拒绝、用户新选模式被旧还原目标覆盖。模拟队列首次无响应，验证第二次收到的是同一歌曲和队列；目标暂停、播放后暂停、Changing、位置变化、缺失媒体、取消、不同／不明／多窗口标题均不补发；未确认不延长期限。现有单次投递及 Mac 默认不重试保持。

选歌仍为十五热门加十五全曲库、每轮三十首、零明确现场版、会员同等参与；无账号操作、云歌单改动、音频下载、新依赖或系统环境修改。Mac 共享模式读回修复，但在线播放缺已登录真机证据，仍为试验适配；双架构 DMG 构建不等于实机播放验收。
