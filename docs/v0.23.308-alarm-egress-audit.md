# v0.23.308：本地闹钟音频与 Egress 审计

## 本次实际修复

检查的是 v0.23.307 的现有 PySide6 架构。闹钟原本就是本地 JSON 配置、本地导入音乐和本地调度；没有发现闹钟 Supabase 表、Storage 下载或 Realtime 订阅。不能把原来不存在的云端请求当作本次减少的流量。

Windows 实机原生测试发现：WAV 使用 WinMM/MCI `waveaudio play repeat` 返回 259；测试 MP3 在此设备的 MCI `open` 返回 277，进入 Qt 回退。旧 Qt 回退通过 GUI 的 EndOfMedia 回调再次 play，续播依赖界面事件循环；同一个 MCI 错误回调重复到达还能重新 setSource/play，重启当前音乐。这些是已证实的播放中断风险，不是每秒 scheduler 反复响铃。

另有停止所有权问题：旧卡片清理使用 process-wide request_stop_all，能误停新试听/闹钟；Windows Qt 回退原先只静音、等待 drain，未确认真正 stop。现在共用 AlarmAudioService，旧音频实际清理完成后再开始下一项；每个动作只停止自己的所有者。全局停止仅用于退出。

Windows Qt 回退使用原 QMediaPlayer/QAudioOutput，通过 QtThreadAudio 命令桥从创建起在同一音频线程运行。加载、play、原生 loops 与 stop 均在该线程；没有迁移已播放的原生播放器，没有新增音频库。QThread 的 finished 早于线程内 DeferredDelete，因此先用 wait(0) 非阻塞确认清理，再删除线程对象，避免 GUI 在 QThread 析构中隐式等待。按钮不 join 原生停止线程。应用退出统一停止并短暂等待。

本地 AlarmManager.update 的无变化提交原先仍写 JSON、增加 generation、清除 occurrence；标签或音量修改可能让刚关闭的日闹钟重新具备触发条件。现在无变化直接返回；只有时间、重复规则或启用状态真的变化才重置 schedule claim。编辑页使用 dirty 草稿，取消/关闭即停试听；持久化 claim 在播放前完成。

## 音频排查：15 项

1. **音频库**：PySide6 6.11.2 Qt Multimedia（QMediaPlayer/QAudioOutput）；Windows 优先既有 WinMM/MCI，解码失败回退 Qt。没有 pygame/mixer。WAV 不再尝试不支持的 MCI repeat；MCI open 277 按文件路径、mtime、size 缓存失败，文件变化重新尝试，缓存有界。
2. **默认与自定义**：调度、所有权和停止共用 AudioService。系统/默认音仍为 QApplication.beep 的短提示；没有捏造一首内置歌曲。自定义文件走 MCI/Qt 原后端，不替换用户音乐。
3. **scheduler**：PetWindow 的一个 precise singleShot QTimer 对齐北京时间每个整秒，再 rearm；每次只是本地 claim_due。页面不创建另一个 scheduler。
4. **重复 trigger**：已有持久化 last_triggered_slot 和 active claim；本次增加播放层 occurrence 去重并修复无变化保存重置 claim 的路径。没有发现每秒重复 play 的证据。
5. **多个 after loop**：该项目是 Qt，不是 Tkinter；没有 alarm after 循环。音频交接的 50ms singleShot 仅在等待旧后端停止时工作，不是数据库/响铃轮询。
6. **重复 load**：旧重复错误回调能重复 setSource；已阻止。卡片路径只加载一次，EndOfMedia 不再手动重载或 play。试听新选择才加载新文件。
7. **重复设备初始化**：未发现每秒初始化设备/mixer。Qt 后端按一次播放生命周期创建，不因刷新重复创建；Windows 试听的 Qt 回退延迟到真正需要时创建。试听与正式响铃至多一个在播放，交接等待旧后端清理。
8. **GUI 主线程**：UI 选择、状态和本地原子 claim 仍在 GUI；MCI 工作在原 daemon worker，Windows Qt 加载/解码/播放/stop 在音频 QThread。macOS 保持原 Qt Multimedia 的异步加载与原生解码，停止沿用既有 Qt 路径。用户导入文件的复制仍是显式设置操作，不在到点响铃路径。
9. **buffer**：没有应用层固定 PCM buffer 参数；由 Qt/系统原生后端管理。本次没有盲目增大 buffer，也不声称有一个不存在的 buffer 数字。
10. **WAV/MP3**：真实 Windows、音量 0、合成 WAV 与 Qt 官方测试 MP3。最终音频桥各运行约 10 秒：WAV 107 次进度变化、跨曲尾 1 次；MP3 197 次进度变化、跨曲尾 1 次；均无 QMediaPlayer 错误，停止确认成功。同进程连续切换通过。测试文件仅在仓库外，不进入安装包。
11. **试听与正式闹钟**：共用 QApplication 拥有的 AlarmAudioService、原 MCI/Qt 后端和停止规则；正式闹钟优先，试听不能打断已响闹钟。
12. **occurrence**：alarm_id + 已持久化的 last_triggered_slot；播放层本轮运行有界 ID 集合，配置层 durable claim 防重启重播。试听用独立生成序号。
13. **dismiss 后再次响**：关闭标记持久化；同 occurrence 不再 play；标签/音量及未改动保存不清空已消费 slot。每日重复的下一天是新的 occurrence，仍应正常触发。
14. **snooze**：先按所有者停止音频，再由现有 AlarmManager 记录 snooze_until；MCI/Qt 完成确认前不启动新的音频。不是仅静音留着无限循环。关闭、开始工作和稍后提醒共用停止路径。
15. **根因范围**：实测 MCI WAV repeat 不支持、此设备 MP3 MCI 解码失败，叠加回退的 GUI 续播和重复加载；全局 stop 与静音 drain 是交接/关闭风险。本次原生播放器进度、停止与焦点验证通过，未试听或读取用户原音乐，不能据此保证所有损坏文件、所有声卡驱动或系统独占模式绝无卡顿。

## Egress / 请求审计：17 项

1. **AlarmScheduler 是否访问 Supabase**：没有，claim_due 只读共享本地内存并在 claim 改变时原子保存 JSON。
2. **优化后是否完全本地**：是；原本已是本地，本次未新增云端依赖。
3. **闹钟表读取频率**：不存在远端闹钟表读取；AlarmManager 初始读取 alarms.json，页面复用当前实例。闹钟列表 render 不查询云端。
4. **取消哪些读取**：本次没有可取消的闹钟云端读取；减少的是无变化本地写、重复音频加载及每秒诊断日志。其他既有业务缓存策略不冒充新优化。
5. **dirty 写入**：编辑草稿无变化不能提交；manager 同值 update 不写本地 JSON。真正修改一次保存本地一次。没有增加云端写。
6. **保存闹钟远端请求**：0；正常真实修改是一个本地原子保存。关联待办已有独立同步机制，不能把待办业务请求错误算作闹钟表请求。
7. **snooze 高频写入**：没有远端写；点击时本地保存一次，倒计时不上传。
8. **ringing/audio position**：不上传；进度仅音频线程与本地 Qt 信号。状态机不含数据库逻辑。
9. **heartbeat**：不读/携带闹钟。约 15 秒一次；字段白名单为 user_id、session_id、working、session_active、session_started_at、input_idle_seconds、last_seen_at、device_id、sequence。Supabase 原子 RPC 只传其中 7 个 p_* 参数，用户与服务端确认时间由服务端处理；不附带时长汇总、计划、训导授权或订阅。
10. **自定义音乐 Storage**：本地选择文件复制到现有本地铃声库，不上传 Storage，不生成签名 URL。
11. **Storage 缓存/版本**：不适用；没有 Storage 下载链。没有为不存在的场景增加下载、全文件 hash 或定时校验。MCI 解码失败缓存只做本地 file fingerprint。
12. **render 重复 select**：闹钟页面没有 select。计时和普通 repaint 不读远端闹钟数据。
13. **组件各查一份**：没有；列表、编辑、卡片、scheduler 复用 window 的 AlarmManager 和 AlarmSoundLibrary。
14. **共享 Store/cache**：保留已有共享 AlarmManager，不另建重复配置 Store；仅新增共享播放所有权服务。
15. **SELECT ***：闹钟无 SQL。本次无数据库结构或 migration。既有搭子、订阅、计划、互动采用限定 RPC/字段、分页/缓存；未对整个项目声称零 SELECT *，兼容 transport 的详情查询需要按原业务处理。
16. **网络 pending/backoff**：闹钟没有云端 pending，不添加空的重试队列。离线仍正常响铃；本地文件失败按已有错误路径处理。其他专注/待办同步保留原持久队列与后台重试，不每秒重试音频。
17. **减少程度**：闹钟普通运行的远端请求 **0 → 0**，不能宣称下降 90%。一次无变化保存本地写 **1 → 0**；重复错误导致的音频加载 **多次 → 1 次/播放**。真实整体账号 egress 需按响应大小与运行行为测量，没有用户运行样本就不编造百分比。

## 优化前后请求模式

| 动作 | v0.23.307 | v0.23.308 |
|---|---|---|
| 本地 scheduler 运行 1 小时 | 约 3600 次本地检查，0 远端 | 相同；不写每秒阻挡日志 |
| 打开/刷新闹钟页 | 0 远端，共享本地配置 | 相同 |
| 无变化保存 | 1 本地 JSON 写，重置 claim 风险 | 0 写，0 远端，保留 claim |
| 真正修改闹钟 | 1 本地保存，0 远端 | 相同，保留非排程修改的已消费 slot |
| 响铃、循环、关闭、snooze | 0 远端 | 0 远端，按音频所有者处理 |
| 重复 MCI 失败回调 | 可能重复 Qt setSource/play | 一次加载与 play |
| 自定义音乐响铃 | 本地文件；无 Storage 下载 | 相同，原生循环 |
| 登录后的后台搭子快照 | 90 秒共享缓存/单飞，辅助资料 300 秒 | 相同，不绑定闹钟 |
| 计划/训导配置 | 对应页面进入、保存、主动刷新 | 相同，不绑定心跳 |

这些是代码频率与行为，不是 Supabase 账单实测。登录后 heartbeat、同步等独立业务仍会发生。当前 online TTL 120 秒，180 秒 grace 表示暂时不确定而不宣称在线；长期无确认统一离线。纪律/coaching delta 约 60 秒；本地 FocusSession checkpoint 60 秒、云端 checkpoint 15 分钟，重要状态/正常退出封存；历史恢复 300 秒。互动页可见时复用既有 dashboard callback，读取有节流、最多最近 7 天 30 条，发送者批量获取；隐藏时不读取 Feed。没有为了音频另开这些请求。

## 可选本地测量

`LILI_NETWORK_DIAGNOSTICS=1` 才记录实际成功 HTTP 响应 body 字节及耗时，覆盖 social.py 现有三条传输路径；默认关闭，不改变全局系统配置。不记录 token、请求体、响应正文、查询参数或用户路径，不上传日志、不额外发送计量请求。复用原有旋转日志（1MiB、3 份备份）。这是客户端响应字节，不包含所有 TLS/header/CDN 流量，也不等于 Supabase 最终计费数；HTTP 失败响应和其他模块的请求不计入这项统计。

Egress 包括服务端返回客户端的数据库/Storage/Realtime 等数据，不能只按“上传次数”判断。参见 [Supabase Egress](https://supabase.com/docs/guides/platform/manage-your-usage/egress)；原生循环语义见 [Qt QMediaPlayer loops](https://doc.qt.io/qt-6/qmediaplayer.html#loops-prop)；MCI repeat 支持范围见 [Microsoft MCI play](https://learn.microsoft.com/en-us/windows/win32/multimedia/play)。

## 验证、兼容与边界

- 既有本地 alarms.json/alarm_sounds.json 字段保留，无数据库变更、无私有素材或测试音频加入发布包。
- 针对测试涵盖播放 ID 去重、优先级、原生/Qt 停止交接、旧所有者隔离、pending 替换取消、无变化保存、标签/音量不重播、次日正常响铃、重复回退回调、编辑 dirty 和诊断隐私。
- 真实 Windows 集成：试听 MP3 → WAV 闹钟 → 关闭 → MP3 闹钟 → 关闭，实际 stop 完成、旧所有者不能停止新播放器，GetForegroundWindow 保持原 HWND。只测试自身窗口、全程静音；没有录音或访问其他应用内容。
- macOS 继续使用原 Qt 后端，通过 ARM/Intel CI 构建与测试；本机未进行 macOS 声卡听感测试。macOS 原生窗口测试沿用既有 headless 排除，不包装成实机听音结论。
- 音频 worker 停止有明确完成确认；极端驱动停止不返回时不会允许另一项叠加播放。应用退出的短暂等待只用于关闭阶段。
- 编译检查、完整测试、三平台 build 和发布资产校验由现有门禁执行。现有系统 py launcher 不可用，本次使用已验证的项目 .venv，未安装系统软件。
