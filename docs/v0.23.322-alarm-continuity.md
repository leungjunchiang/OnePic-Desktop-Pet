# 自定义闹钟连续性修复

## 日志证据与边界

2026-10-03 北京时间 11:30 的自定义 MP3 闹钟：旧 Windows MCI 接口报 open failed: 277；11:30:00.102 切 QtThreadAudio，00.375 BufferedMedia，01.083 LoadedMedia。LoadedMedia 表示已停止（Qt 官方 QMediaPlayer 状态定义：https://doc.qt.io/qt-6/qmediaplayer.html）。用户到 11:30:17 才点关闭，中途没有关闭按钮、默认铃声截止时间或第二个闹钟替换的记录。因此日志支持“自定义备用后端约一秒后意外停止”，不是用户误把 17 秒后的关闭当成铃声结束。

旧日志未记录该后端 playbackState / position / stop 调用，不能确定导致原生 stop 的具体调用或驱动条件。相同文件静音测试超过六秒未复现，不把 MCI 错误本身说成最终停播原因。

## 实际修改

- alarm_audio_service.py / _QtAudioWorker：独立线程原生循环，250ms 轻量检查。仅有播放意图且处于无错误 LoadedMedia/EndOfMedia 的非播放状态时恢复；留 750ms 给原生循环自行续播。播放和加载/缓冲中不 restart、不 setSource。恢复保留最后非零有效位置（Qt stop 可能先发 position=0 再发 StoppedState）；循环确实结束从零开始。
- 30 秒最多恢复三次；仍不能连续播放走既有系统提示音备用路径。error、显式 stop、关闭/稍后提醒、退出先停止恢复。自然结束的有限次数媒体不重播。
- QtThreadAudio 显式 DirectConnection 在新线程 initialized；所有 source/loops/volume/play/stop 使用 QueuedConnection，播放命令不能先于初始化。
- alarm_ui.py：Mac 自定义正式铃声和试听复用 QtThreadAudio，不在 GUI 做原生解码和 stop。试听停止清空旧桥，下一次重新创建，并沿用音频所有权与原生清理完成门禁。Windows 继续既有 MCI / Qt 解码备用方案。
- 本地生命周期日志新增 worker.state / progress（5 秒一次）/ resume / recovery_exhausted / stop、bridge.stop_requested、audio.retire 和 card.stop.intent。无媒体文件内容、歌词或路径上传，无网络查询或新数据库结构。

## 验证

tests/test_alarm_continuity.py 含 11 项：一秒意外停播位置恢复；加载、缓冲、暂时停顿、错误不重复播放；自然循环/有限播放结束；有限重试；停止回调竞态；Mac 使用既有桥；真实 Windows 两秒 WAV 连续循环及 GUI 忙碌；真实原生 stop 故障注入后恢复断点。真实测试全程静音，不修改用户配置。无声卡 runner 跳过原生设备验证，Mac 无头环境跳过真实卡片及 Windows 设备测试。现有音频交接、退出、弹窗焦点和完整平台测试仍需通过发布门禁。

不是所有硬件/损坏媒体文件都能保证无中断。设备移除或媒体解码失败会使用既有 fallback；无需重置卡、不删除铃声或历史。GUI/CPU 严重阻塞和物理设备播放流畅度仍以用户实机为准。
