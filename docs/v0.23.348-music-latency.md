# v0.23.348 · 加快 QQ 随机与歌单选曲

用户反馈随机起播、双击歌单歌曲都慢。本机先按生产入口逐阶段计时，再优化；没有以缩短歌曲加载超时或跳过播放确认冒充加速。

## 延迟原因与修改

1. QQ 歌曲详情页真实公开了播放栏，但把五个相关控件中的四个标记为离屏。原有就绪扫描过滤后只剩一项，持续等待二十五秒仍失败。现在仅在正常可见判断为 loading、合并离屏证据构成完整播放栏且无登录／验证／登录中阻断时，再用现有的唯一同栏模式读取复核。无法读回仍不就绪；不把隐藏登录提示当成账号退出，也不越过认证提示。
2. 已有唯一 QQ 客户端的完整正向就绪证据只读一次即可继续，投递前仍重新确认进程及模式。真正冷启动仍普通启动一次，保留两次稳定观察、至少两秒登录恢复和原有总等待上限。
3. 模式已经是目标值时，不再重复读第二次。Windows 原生队列在 ID 投递之前确认一次顺序模式，歌曲匹配后复用同一次准备结果，不再重复开两个模式 helper。每次选曲仍有新的投递前模式检查；非原生适配仍使用原有播放后模式准备，不做长期模式缓存。
4. 公开歌手目录的完整匿名分页在歌单旁缓存十分钟，跨重启复用原有热门排序及全部候选元数据；过期、未来时间、损坏或不完整缓存重新查询。缓存读回仍走相同歌手、类型、版本、时长、授权解析；不能写缓存也正常播放。唯一临时文件原子替换并清理，不存音频、登录信息或用户会员状态。
5. 被动媒体检查正在运行时，用户的随机或选曲请求排队优先执行，保留最新请求；选曲按 ID 重新定位，避免换轮后误播同一行号。暂停或退出会清除待播请求，旧检查结果不再覆盖它。歌单双击被接受时立即显示“正在切歌…”，播放确认后才显示正在播放。

## Windows 实测

QQ 已运行，在真实管理器入口随机并连续选曲，均确认目标歌曲正在播放；测试用独立三十秒暂停守护，脚本 finally 也暂停。

| 场景 | 优化前可用基准 | 优化后本机样本 |
|---|---:|---:|
| 无持久缓存的随机起播 | 11.563 秒 | 9.266 秒 |
| 新进程复用十分钟内目录随机起播 | 原版本不跨进程缓存 | 4.453 秒 |
| 歌单第 2 首 | 6.281 秒 | 2.750～3.234 秒 |
| 歌单第 5 首 | 7.219 秒 | 3.281～3.516 秒 |

原始首次基准另遇到 4.734 秒目录查询加 25.578 秒就绪误等待，总计 30.391 秒后拒绝播放。它是误判失败，不计作成功播放耗时。修复离屏判断后获得上表优化前可用基准，再比较减少重复检测的效果。

跨进程缓存样本目录解析 63ms、零目录 HTTP 请求。样本为本机本次客户端、网络和所选歌曲结果，不承诺所有电脑恒定耗时；首次无缓存仍需查询公开目录，QQ 本身启动及联网加载仍会耗时。

另用真实 Qt 控制器、音乐工作线程和歌单双击信号连到真实 QQ 验收：目录过期回源时随机确认约 10.875 秒；双击第 2 首约 3.578 秒、第 5 首约 2.907 秒，界面立即显示正在切歌，结果确认后显示正在播放。Qt 窗口离屏运行，避免干扰用户桌宠和专注记录；没有用假播放器代替这一轮 QQ 播放。

继续保持每轮三十首、热门十五加全曲库十五、完整版本去重、零明确现场版及会员同等随机。ID 队列、暂停优先和自然曲终规则不变。不操作登录或关闭 QQ，不增加云端请求／数据库变更。Mac 同享目录缓存和界面请求优先处理，但没有已登录真机的播放测速；在线功能仍属试验适配。

回归涵盖错误离屏完整栏、认证阻断、已有／冷启动、单次模式准备、跨进程缓存及到期／损坏／写入失败、慢检查期间请求优先、最新选择、按 ID 追踪和暂停／退出清队列。公开发行继续完整 Windows 和双架构 Mac 测试、冻结启动及安装包检查。
