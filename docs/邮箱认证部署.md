# 邮箱注册部署说明

## 开发端一次性自动配置

终端用户不需要填写 SMTP 信息。仓库提供了 `configure-supabase-auth` GitHub Actions 工作流和 `scripts/configure_supabase_auth.ps1`，由开发者在部署端一次性写入 Supabase Auth。

在 GitHub 仓库的 Settings → Secrets and variables → Actions 中只需配置以下四个 Secrets：

- `SUPABASE_ACCESS_TOKEN`：Supabase Management API 细粒度 Token；
- `SUPABASE_SMTP_HOST`：邮件服务商 SMTP 主机；
- `SUPABASE_SMTP_USER`：SMTP 账号；
- `SUPABASE_SMTP_PASSWORD`：SMTP 密码或授权码。

项目 ID 和确认跳转地址会自动从公开的 `config/social_backend.json` 读取；SMTP 端口默认 `587`，From 邮箱默认使用 SMTP 账号，发件人名称默认使用 `Lili`。如果邮件服务商要求不同的 From 地址或端口，再额外设置 `SUPABASE_SMTP_ADMIN_EMAIL`、`SUPABASE_SMTP_PORT` 和 `SUPABASE_SMTP_SENDER_NAME` 即可。

`SUPABASE_ACCESS_TOKEN` 应使用 Supabase Management API 的细粒度权限，至少包含 `auth_config_write` 和 `project_admin_write`。然后在 Actions → `configure-supabase-auth` → Run workflow，项目 ID 和跳转地址输入框可以留空。

工作流只在手动触发时运行，不会在 Pull Request 中暴露密钥。脚本不会打印 SMTP 密码或 Supabase Token，也不会把它们写进客户端。以后更换 SMTP 服务时只需更新 GitHub Secrets，再重新运行工作流。

Lili 的注册使用 Supabase Auth 的邮箱密码认证。桌面端已经处理了两种正常返回：

- 已开启自动确认时，注册后立即进入账号状态；
- 开启“Confirm email”时，注册接口返回“已创建、等待确认”，界面会显示成功提示并提供“重新发送确认邮件”。

## 为什么 163/学校邮箱收不到

Supabase 的默认 SMTP 仅用于演示和测试，通常只允许项目组织的团队成员邮箱收件，并且发送限额很低。它不适合给 163、edu.cn 或其他普通用户邮箱投递确认邮件。

生产发布前，请在 Supabase Dashboard 的 Authentication → Emails → SMTP Settings 配置自定义 SMTP（例如 Resend、Amazon SES、Postmark、SendGrid、Brevo 或其他 SMTP 服务），并设置：

1. `From` 地址使用已验证的域名；
2. 按邮件服务商要求配置 SPF、DKIM 和 DMARC；
3. 在 Authentication → URL Configuration 中允许当前 `email_redirect_to`，本项目默认是仓库首页；
4. 在 Authentication → Rate Limits 中按预计注册量调整邮件限额；
5. 使用“重新发送确认邮件”验证 163、学校邮箱、Gmail 等至少三类收件人。

不要把 SMTP 密码、API Key 或 Supabase secret/service-role key 写入仓库、安装包或客户端配置。

确认链接打开仓库首页是当前桌面端的既定回跳页，不代表注册失败；确认完成后回到 Lili 的“我的 → 登录”页即可登录。若希望展示自定义网页，需要另行部署并把该网页加入 Supabase Auth 的 Redirect URLs allow-list。
