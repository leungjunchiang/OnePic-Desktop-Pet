# 闹钟响铃但处理窗口不可见

## 代码根因与证据范围

v0.23.324 的 PetWindow._show_alarm_card 直接调用 _passive_surfaces_blocked；该函数把普通 quiet mode（如游戏、录屏、会议进程）、宠物手动隐藏和真正全屏都视为不能展示。已触发 occurrence 会走 start_alarm_suppressed，音乐正常响，但控制卡无原生窗口。没有恢复调度，除非用户手动打开闹钟中心，它会一直没有处理入口。用户确认本次发生在普通桌面；读取本机可访问的 runtime/lifecycle 当前轮转日志没有找到这次闹钟的对应记录，不能从日志断言当时具体哪一个门禁命中。上述代码路径和回归可复现该类故障。

另有两项耦合：闹钟被放进宠物附属浮层清单，隐藏宠物也隐藏闹钟；手动打开闹钟中心会先显示待处理卡，随后打开编辑器并激活，遮挡刚显示的处理入口。

## 修复

- _alarm_ui_block_reason 只判断真正全屏/退出；消息门禁和宠物可见性不决定已触发闹钟的处理窗口。既有 claim_due 和 alarm.allow_during_dnd 仍决定是否触发、认领 occurrence，未改变用户的响铃配置。
- 闹钟退出宠物附属浮层清单，改由 _sync_alarm_card_visibility 管理。全屏时 defer_alarm_ui 只隐藏控制，不停止音乐、不确认事件；正常桌面恢复同一张未处理的卡。
- 复用现有 750ms 前台状态检测及两次稳定采样，包括全屏短于宠物隐藏 debounce 的情况。没有新增 scheduler、网络 worker 或 Supabase 请求。
- show_alarm_center 优先提供仍待处理的控制卡，不额外打开编辑器。没有未处理闹钟时仍打开原编辑页。
- AlarmCard.show_alarm_foreground 保留 ACKNOWLEDGED 状态，已关闭/请求处理的卡拒绝显示；_audio_started 保证展示恢复不再次启动音频。第一次显示才居中，恢复尊重用户拖动位置；用户自行最小化的卡不自动展开。
- 无 focus/activate/raise/grab 调用；沿用 WA_ShowWithoutActivating、WindowDoesNotAcceptFocus 和 Windows 非激活原生窗口策略；Mac 复用现有 Cocoa 非激活浮动层级桥，避免后台应用的控制卡沉在当前应用后面。不是将普通搭子互动放宽为主动桌面窗口，历史互动继续静默。

## 验证

tests/test_alarm_visibility.py 用原生窗口无关的卡片替身覆盖所有平台的门禁、时序、生命周期与入口；tests/test_alarm_ui.py 在支持的 GUI 环境验证实际卡片恢复音频只启动一次、已确认状态不重置、关闭后不复活。macOS 无头 CI 沿用原有真实 AlarmCard 模块跳过，政策回归仍运行。

Windows 本机原生插件测试 test_native_alarm_show_and_restore_do_not_change_foreground 创建静音实际卡片，反复显示/隐藏/恢复，比对 GetForegroundWindow 保持一致。CI 无头环境跳过原生 HWND 检查。发布仍经过 Windows、Mac ARM 与 Intel 的完整测试和打包；没有执行系统重启或播放测试音乐，不改专注、闹钟设置或用户历史，无需重置卡。
