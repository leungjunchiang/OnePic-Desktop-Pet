# v0.23.303 勾选绘制与 FocusSession 开工核查

## 1. 勾选框的代码根因与修复

项目是 PySide6 / Qt，没有 ttk、BooleanVar 或 Tk scaling。普通设置此前使用原生 `QCheckBox` indicator，指定/严格训导搭子使用 `QListWidgetItem.CheckStateRole` 和原生 delegate indicator。两者由系统/Qt style 绘制，并受局部样式表影响；待办条还单独设置了圆形填充 indicator、没有应用绘制的 tick。选中行焦点线仅表示焦点，不能表示布尔值。

代码可以确认对原生 indicator 的依赖。仅凭两张截图，不能精确判定另一台电脑具体是 Windows 主题、Qt style 还是 DPI 触发，不能宣称已在那台设备直接复现。新版将这些变量从勾选绘制中移除，并验证后端、模型和画面一致。

`check_controls.py` 提供：

- `draw_check`：QPainter 圆角方框与矢量白色 tick，不使用 Unicode 勾，也不依赖字体 fallback。
- `AppCheckBox`：继承 QCheckBox，保留 clicked、toggled、布尔状态、键盘 Space、可访问性；框与文字都可点击。20 个逻辑像素由 Qt 映射 DPI。
- `CheckItemDelegate` / `CheckListWidget`：保留列表原文本、选中、编辑模型和点击区域，在实际 indicator 矩形统一绘制。
- 未选中为白底深边；选中为青蓝填充白勾；hover 加深；禁用选中为灰蓝填充白勾，禁用未选中为浅灰空框。焦点为独立虚线边界，不覆盖勾。

统一覆盖训导、工作计划、指定搭子、严格资格、提醒/隐私、我的设置、闹钟、搭子授权、投喂选择、今日便笺与待办设置。原业务 handler 和服务端权限没有改成另一套系统；移除了待办条冲突的 indicator 样式。提醒菜单的 checkable QAction 继续是菜单动作，未把菜单重做成表单。

真实 Qt 渲染与点击测试覆盖 Fusion / Windows style、四种 checked/enabled 组合、文字点击、Space、列表选中/禁用与模型切换、服务端授权 true 的实际应用。另在独立进程用 125% / 150% 缩放执行测试和生成设置页截图；白勾无裁切。没有声称已在所有 Windows OEM 电脑实际运行。

## 2. 开工事实来源与统一函数

工作报告蓝色时间块来自 `FocusAnalyticsStore` 的原始 `records`（started_at + seconds 或 start_at/end_at），转换为不可变 `FocusSegment`，加上当前本机真实 timer 工作段，再按区间并集绘制。标量累计值、图形坐标、旧纪律 actual_start 不是时间块的事实。

`discipline.focus_start_index` / `get_actual_work_start` 复用这些缓存事实：

1. 使用未经日界线/06:00 裁剪的原始 start。
2. 转为电脑本地时区。
3. 按 `(device_id, session_id)` 取得会话最初 start，云端 checkpoint 分段不产生新会话。不同设备相同 session_id 不混合。
4. 选择本地日期 D 且 start >= D 06:00 的最早值。
5. 排除无效、未来、不可信累计 checkpoint、heartbeat/恢复伪造条目，以及远端 presence live 投影。
6. 新版明确用户操作标记 `explicit_focus_start` 可补足尚未封存的开始几秒；没有增加新的高频开工同步机制，沿用已有每天首次纪律事件。旧来源不明事件不能压过原始事实。
7. 没有合法事实或可信新操作时返回 None，显示「尚无开工记录」。

| 页面 / 入口 | 调用链 |
|---|---|
| 工作报告 | `build_work_report` → 同一 analytics 缓存 `range_segments` + 本机活动段 → `get_actual_work_start` |
| 今日 / 本周 / 历史 | `PetWindow._discipline_focus_sessions` → 同一 analytics 缓存 + timer → `DisciplineEngine.work_start_index` / `daily_summary` → `get_actual_work_start` |
| 实时迟到 / 结算 | `DisciplineEngine.actual_work_start` 与 `daily_summary`，不使用登录/页面时间 |
| 搭子可见纪律摘要 | 已有权限过滤 RPC 调用 `lili_actual_work_start_clock`，按相同设备/会话取原始事实最初 start；完整权限检查保留 |

示例 00:18、08:52、09:14 的区间：实际开工 08:52。05:40–06:30 的会话，其 06:10 checkpoint 不算 06:10 开工；下一次真实会话 08:12 才是实际开工。跨午夜延续到当天的 checkpoint 也不能制造新 start。蓝块可能跨越 06:00，判定依据其原始会话 start。

旧 v0.23.302 的独立 start_work=16:26 等 unknown 值只保留作历史兼容数据，新页面从已存在的 08:52 专注事实显示正确开工；不因旧字段非空而优先采用。旧累计且没有可信区间的数据不能补造时间。

## 3. 历史与迟到

- 读取时动态推导，不启动几百天逐日查询，不上传历史补造事件，不逐日 update。
- 报告与纪律共用同一个 AccountFocusStore 已加载缓存，不为开工发额外 Supabase 请求。
- 一次渲染构建会话 start 索引，本周/历史复用；历史页面仅进入后展开，能发现只有专注区间、没有纪律事件的日期。
- 历史完成时长由一遍本地范围汇总提供，选中日期复用缓存；原始自然日时长不改成 06:00 日界线。
- 历史计划优先使用当日结算/迟到/可信开工事件里保存的 planned_start。没有当日快照，仍恢复实际开工，迟到显示「缺少历史计划基准」，不拿现在的通常开工回算过去。
- 有可信计划时重新计算 `max(0, actual_start - planned_start)`；当日免战为零。被原始事实纠正为准时的旧迟到不进入当前纪律摘要的待说明。
- 历史补全只影响展示，不回写或重发历史惩罚/说明记录；旧原始数据保留。

## 4. 数据库、性能与边界

没有新增开工表，也没有历史全量 backfill。扩展已有幂等部署 bundle：增加 `(user_id,device_id,session_id,start_at)` 查询索引，更新原开工摘要函数及缺少历史计划时返回 null 的展示。按当日 session seeds 批量寻找原始起点；内部函数仍不可由客户端直接执行，搭子摘要保留逐字段授权。真实 SQL 回滚测试新增 FocusSession 推导、06:00 前 checkpoint、unknown legacy 优先级。

服务端历史没有记录 UTC offset 时沿用既有中国时区日历；桌面使用当前电脑本地时区。没有区间或丢失最初 checkpoint/session identity 的极老记录不能完整推断原始开始，继续保留未知；不会人为补造 00:00/06:00。无法读取另一台电脑尚未上传的专注段，因此跨设备事实同步仍受现有 15 分钟 checkpoint 和重要边界上传影响。

本次不更改心跳、订阅持久性、专注安全保存及增量 ACK 频率。新测试覆盖真实像素、Boolean 绑定、checkpoint、跨午夜、跨设备 ID、时区、历史计划、免战、历史无写回及报告/摘要统一来源；发布继续执行完整回归、数据库真实回滚与三平台构建门禁。
